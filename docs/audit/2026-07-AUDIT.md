# SimpleAM Codebase Audit — July 2026

**Date:** 2026-07-28
**Scope:** Full repository — architecture, code quality, security, database, UI/UX, accessibility, i18n, testing, CI/CD, observability, documentation.
**Baseline:** 87,025 LOC across 524 `.ts`/`.tsx` files · 48 Prisma models · 59 routes · 16 API routes · 190 server actions · 39 test files · 8 locales.
**Status at time of audit:** pre-release, no production users.

This document is the evidence record for the remediation programme. GitHub issues reference it rather than restating findings, so the issues can stay short and the reasoning survives after they're closed.

Every figure below was independently verified by direct inspection, not inferred.

---

## Executive summary

The codebase is not uniformly poor. Several areas are genuinely well built (see [What is already good](#what-is-already-good)). The defining problem is different and more specific:

> **The right abstractions were built and then never adopted, and the safety nets report success without checking anything.**

Three findings characterise the whole repository:

| | |
|---|---|
| `lib/actions/safe-action.ts` | A complete server-action wrapper — auth, Zod validation, org scoping, uniform result type. Its own docblock says *"Every server action should use `createAction()`."* It has **zero importers**. All 190 actions copy-paste a 12-line preamble instead. |
| `vitest.config.ts:18-23` | Declares 80% coverage thresholds. CI runs `vitest --run` **without `--coverage`**, so they are never evaluated. Real coverage is roughly 8%. |
| `.github/workflows/qa.yml:63-95` | Two jobs named "Visual **Placeholders**" and "Accessibility **Placeholders**". They are green because 6 of 7 tests are `test.skip()`. |

The consequence is that no signal in this repository can be trusted without verification. That is why the remediation programme front-loads making the signals honest, before doing any of the actual cleanup.

## 1. Broken right now

These are defects in current behaviour, not technical debt. Because the product is pre-release they are **launch blockers** rather than incidents — but one of them (signup) blocks all end-to-end testing and therefore gates most other work.

### 1.1 Signup is dead on arrival — `P1`

`app/api/auth/callback/route.ts` calls `supabase.auth.exchangeCodeForSession(code)` and redirects. It never creates the corresponding `Organization`/`User` rows in Postgres.

Any subsequent `/dashboard/*` page or action calls `requireUser()` → `getCachedUserWithOrganization()` → `prisma.user.findUnique({ where: { id: supabaseUser.id } })`, which returns `null`. `requireUser()` then throws `Unauthorized: User must be authenticated` — for a user who has just successfully authenticated. There is no self-service recovery.

`lib/auth/cached-user.ts` already contains `ensureUserWithOrganization(user)`, which does exactly the right thing. **It has zero callers.**

> Tracked as existing issue **#136**.

### 1.2 Account takeover via unverified email — `P1`

`lib/auth/cached-user.ts:146-163`:

```ts
const existingByEmail = await prisma.user.findUnique({ where: { email: user.email || '' } })
if (existingByEmail && existingByEmail.id !== user.id) {
  const updated = await prisma.user.update({
    where: { id: existingByEmail.id },
    data: { id: user.id, ... },   // rewrites the primary key to the new Supabase ID
  })
```

Any new Supabase identity whose email matches an existing user **takes over that user's row** — inheriting `organizationId`, `permissions[]`, `roleNames[]`, and `isPlatformAdmin`. There is no `email_confirmed_at` check, no provider allowlist, and no consent step.

**This is currently dormant only because the function is never called — which is finding 1.1.** Fixing signup without hardening account linking converts a dormant vulnerability into a live one. The two must ship in a single PR.

### 1.3 ~154 UI elements render with no colour — `P1`

- `tailwind.config.js:17-21` → `primary: 'hsl(var(--primary))'`
- `app/globals.css:2778` → `--primary: oklch(0.646 0.222 41.116);`

The generated declaration is `hsl(oklch(0.646 0.222 41.116))` — invalid CSS, dropped by the browser.

This is partially masked because a **compiled Tailwind v4 stylesheet was pasted into `app/globals.css`** (3,503 lines, containing `@layer theme`, `@layer properties`, `@import "tw-animate-css"` and ~100 `oklch()` literals — all v4 compiler output, in a Tailwind **3.4** project). That paste redefines *some* utilities, but only those that existed at paste time:

| Utility | Defined in the pasted CSS | Usages in `app/` + `components/` |
|---|---|---|
| `bg-primary` | ✅ (`app/globals.css:1228`) | — renders correctly |
| `border-primary` | ❌ | **51** |
| `bg-primary/*` | ❌ | **64** |
| `bg-destructive/*` | ❌ | **32** |
| `ring-primary` | ❌ | **7** |

Every one of those ~154 usages renders with no colour today — invisible borders, colourless focus rings, destructive actions that don't look destructive. **And every new semantic utility written from today onward is also broken.**

### 1.4 A second user in an org cannot save AI settings — `P1`

`prisma/schema.prisma:825-826`:

```prisma
organizationId String @unique @map("orgId")
userId         String @unique
```

Both columns are `@unique`, so only one user per organisation can ever have AI settings. The second user's `create` at `app/api/ai/settings/route.ts:29-34` throws a P2002 unique-constraint violation. Should be `@@unique([organizationId, userId])`.

### 1.5 Recurring event creation silently rolls back — `P1`

`app/actions/events.ts:246-290` generates up to 500 occurrences and then, inside a single Prisma interactive transaction:

```ts
const events = await Promise.all(
  occurrences.map(async (occurrence) => tx.event.create({...}))
)
await Promise.all(events.map(async (event) => tx.eventAttendance.createMany({...})))
```

Prisma interactive transactions default to a **5-second timeout**. 500 creates plus 500 attendance batches will exceed it and roll back the entire series. `Promise.all` over a single `tx` client also serialises on one connection, so it doesn't even gain the intended parallelism. `createMany` is the correct primitive here.

Blast radius: "create weekly training for the season" — a core workflow — appears to succeed and saves nothing.

### 1.6 Cross-permission data leak on spreadsheet history — `P1`

`app/actions/data-management.ts` implements a real ACL (`resolveAccessLevel` / `hasAccess` from `lib/data-management.ts:93,181`) and applies it at lines 223, 301, 489, 564, 610.

But `getRowHistory` (`:92-95`) and `getSpreadsheetHistory` (`:143-146`) both `include: { permissions: true }` — fetching the ACL — and then **never call `resolveAccessLevel`**. They check only `spreadsheet.organizationId !== user.organizationId` (`:97`, `:148`).

Any member of the organisation can therefore read the full mutation history — including `previousData`/`newData` payloads, i.e. who changed which medical or wellness value — of a spreadsheet they have `none` access to. The dangling `include` is direct evidence the check was intended and dropped.

### 1.7 Internal error messages shown to users — `P2`

Raw `error.message` returned to the client at **16 sites**, including `app/actions/events.ts:363,366,455,458,512,723` and `app/actions/platform-admin.ts:65,107,147,188,224,261,302`.

Both client error boundaries then render it verbatim: `app/error.tsx:39-45` and `app/global-error.tsx:52-57`.

Users see Prisma error text; attackers see constraint names, column names and schema shape. Note that commits `42bffe58` and `f33e9462` fixed exactly this class of leak in API routes and pinned it with tests — the client boundaries were missed.

### 1.8 A developer string ships as a translation — `P3`

`messages/ja.json` contains `"errorBoundaryCaught": "ErrorBoundary caught an error:"` as a user-facing value.

## 4. Security

### 4.1 No authorization chokepoint

`middleware.ts` performs **zero** authorization — see §2. The only route-gating function is dead and fails open. The matcher excludes `/api`, so the 16 API routes get no edge-level handling and there is nowhere central to add one.

Every one of ~59 routes and 190 actions must therefore remember its own auth and org-scoping check. The recent commit run — `3ef61eb2`, `86f28902`, `be533fbd`, `4746e179`, `f815e58e`, and ~7 more, all `fix(security): scope X to caller organization` — is direct evidence that this fails repeatedly. There is no defence in depth.

### 4.2 No RLS

`ROW LEVEL SECURITY` appears only in docs (`docs/setup/DATABASE_SETUP.md`, `docs/simpleam.app.md`) and setup scripts — **never** in `prisma/schema.prisma`, the tracked migration, or any applied SQL.

Prisma connects as the Postgres owner via `DATABASE_URL`, which bypasses RLS regardless. Tenant isolation depends entirely on all 79 `findMany`/`findFirst` call sites remembering `where: { organizationId }`. `app/actions/files.ts:13` additionally uses `SUPABASE_SERVICE_ROLE_KEY`, bypassing Storage RLS too.

> Tracked as existing issue **#132** — but as written it is not actionable, because RLS policies cannot be expressed in `schema.prisma` and must ship as migration SQL, which requires §5.1 first.

### 4.3 Rate limiting is decorative

`lib/rate-limit.ts:19` stores state in a module-scope `new Map()`. The file's own header admits it is *"suitable for single-instance deployments"*. On Vercel every lambda instance has its own map and instances recycle constantly, so with N instances the effective limit is N × configured.

Coverage: **2 of 16 API routes** (`app/api/ai/chat/route.ts:29`, `app/api/ai-workspace/suggest-enhancements/route.ts:22`). The `LOGIN`, `FORMS_SUBMIT`, `FILE_UPLOAD`, `AI_INSIGHTS`, `AI_SETTINGS`, `API_DEFAULT` configs are defined and **never used**. Zero rate limiting on login, or on any of the 190 server actions.

Notably unprotected and expensive: `app/api/ai-workspace/generate-agentic/route.ts` (`maxDuration = 300`, spawns an agent against the Anthropic API).

### 4.4 Committed secrets

`backups/backup.sql` — 1.7 MB, git-tracked, added 2026-01-07, **not** in `.gitignore`. Contains `CREATE SCHEMA auth`, 2 `encrypted_password` references, 119 `service_role` occurrences, and real PII including the author's personal email address. A live DB password is also committed at `docs/setup/DATABASE_SETUP.md:295`.

> Tracked as existing issue **#129**.
>
> **Resolved 2026-08-02 (#223), with one part deliberately declined.** The Supabase password was rotated and Vercel's `DATABASE_URL`/`DIRECT_URL` updated across all environments — that is what neutralised this; the copy in history now opens nothing. `backups/backup.sql` was untracked and deleted, `backups/` gitignored, and the live DSN at `docs/setup/DATABASE_SETUP.md:295` replaced with placeholders. gitleaks now runs in CI (#158), scanning the working tree rather than history.
>
> **The dump remains in git history, as an accepted risk.** The repository is private with zero forks, there was never a production user, and the credential is dead — so rewriting 95 commits and force-pushing over `main` was judged the worse trade. **This decision is conditional: if the repository is ever made public, the history must be purged first**, because the dump contains 29 real email addresses and a bcrypt hash.

## 5. Database

### 5.1 Migrations are gitignored

`.gitignore:45` → `prisma/migrations`

```
$ git check-ignore -v --no-index prisma/migrations/20260101000000_new/migration.sql
.gitignore:45:prisma/migrations   → IGNORED
```

Any migration produced by `prisma migrate dev` is silently untracked. `prisma/migrations/` therefore contains exactly **one** directory (`20251118203003_add_platform_admin_flag`, 5 lines of SQL, force-added) for a **48-model** schema. There is **no `migration_lock.toml`**, so `prisma migrate deploy` cannot run reliably.

Corroborating evidence this is `db push` chaos rather than a migration workflow:
- `package.json:144` — `db:push` = `prisma db push`
- `package.json:145-147` — three bash wrappers
- `scripts/migrate-dev.sh:35-56` — the documented fallback is *"copy the SQL and paste it into the Supabase SQL Editor"*
- `scripts/migrate-dev.sh:29-31` — swallows apply failures

**Consequence:** no reproducible schema history, no rollback, no way to verify prod matches `schema.prisma`, no review of destructive DDL. This gates all other schema work.

## Method

- Three parallel read-only sweeps (backend/architecture, UI/design/i18n, testing/CI/DB/security), each instructed to produce file-and-line evidence with counts rather than impressions.
- Every load-bearing claim then independently re-verified by direct inspection before inclusion — several agent claims were corrected in the process (e.g. the `players-table-new` "duplicate" is a 29-line wrapper, not a second implementation; `search.ts`'s `$queryRaw` usage is injection-safe).
- Counts produced by `grep`/`find` over `app/`, `components/`, `lib/`, `hooks/`, excluding `node_modules`.
- `npm audit` figures from `npm audit --json` on the committed lockfile.
- Locale key counts computed by recursive leaf-count over `messages/*.json`.

- CI history and job-level outcomes (§8.4, §8.5) confirmed at runtime via `gh run list` / `gh run view --log-failed` on 2026-07-28.

**Branch protection cannot be configured at all.** `GET /repos/saarbyrne/Simpleamapp/branches/main/protection` returns:

> 403 — Upgrade to GitHub Pro or make this repository public to enable this feature.

So the `.claude/CLAUDE.md` rules "NEVER commit directly to `main`" and "NEVER merge without CI passing" are **convention only, enforced by nothing**. Combined with §8.4 — where four of six jobs fail on every run — there is currently no mechanism, technical or procedural, that prevents a broken change reaching `main`. Any hard gate this programme adds (the build job, the ratchets, the migration parity check) will be advisory until the repository is on a plan that supports required checks, or is made public. Worth deciding early, because most of the guardrail epic assumes enforceability.

**Not verified:** `node_modules` was not installed in the audit worktree, so `npm run build`, `npm run typecheck` and the test suite were not executed locally. CI confirms `Lint & Typecheck` and `Unit Tests` pass, so those two are green regardless.
